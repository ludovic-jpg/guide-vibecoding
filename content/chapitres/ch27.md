Ce livre obéit à une charte. Pas de tiret cadratin, pas de « crucial » ni de « levier », un vouvoiement constant, des encadrés balisés d'une façon précise, des faits datés et sourcés. Pour faire relire un chapitre par Claude, on peut recoller ces règles en tête de chaque conversation. Au dixième chapitre, on en oublie une ; au vingtième, on oublie de coller la charte.

Le chapitre 5 a posé la réponse de principe : ce qui doit être su tout le temps va dans la mémoire, les instructions de projet ou la Knowledge de Lovable ; ce qui doit être su à certains moments va dans une compétence. Le chapitre 4 a fait le tour de la page Compétences, le chapitre 5 a lancé l'ébauche de relecture-manuel. Ce chapitre les prend au sérieux : où elles vivent dans Claude, Claude Code et Lovable, comment profiter de celles des autres, en particulier de Matt Pocock, comment écrire la sienne, et pourquoi certains gestes demandent un hook.

:::mot Discernement et tour de main
Dans l'interface française de Claude, les *skills* s'appellent des « compétences ». La traduction est honnête, mais elle tire le mot vers le diplôme. L'anglais *skill* vient du vieux norrois *skil*, qui désignait d'abord le discernement, la faculté de distinguer une chose d'une autre. Le sens d'habileté, de tour de main, est venu ensuite.

Les deux sens conviennent à l'objet. Une compétence n'apporte pas à Claude un savoir général, il en a déjà beaucoup trop. Elle lui apporte une manière de faire qui vous est propre, et elle suppose qu'il sache reconnaître le moment où elle s'applique. Le tour de main sans le discernement donne un employé qui applique la procédure des factures à une lettre de condoléances. Le discernement sans le tour de main donne un employé qui voit bien qu'il faut une facture et l'improvise. J'emploie ici « compétence » pour l'interface de Claude, « skill » pour le format et les fichiers.
:::

### Le classeur et sa tranche

Une skill est un dossier. Il contient au minimum un fichier SKILL.md, qui commence par un en-tête de quelques lignes (un nom, une description), suivi d'instructions rédigées en Markdown. Le dossier peut contenir d'autres fichiers : des modèles, des documents de référence, parfois des scripts.

Les instructions permanentes sont relues à chaque message et occupent la fenêtre de contexte (chapitre 2). Les skills suivent un autre régime, déjà entrevu au chapitre 4 : l'agent ne lit que le nom et la description de chaque skill, une centaine de tokens, n'ouvre le SKILL.md que si votre demande correspond à la description, et ne consulte les fichiers annexes que si les instructions l'y invitent. La documentation appelle cela la divulgation progressive.

:::fiche DIVULGATION PROGRESSIVE · CONCEPT
**Définition.** Le principe de chargement des skills : l'agent lit d'abord leurs seules descriptions, puis les instructions d'une skill quand la demande y correspond, puis ses fichiers annexes si nécessaire.

**Analogie.** Le classeur de recettes d'une cuisine de restaurant : on lit les tranches d'un coup d'œil, on ne sort une fiche que pour le plat commandé.

**À ne pas confondre avec.** Le RAG des projets de Claude, qui va chercher des passages dans une grande base de documents ; ici, c'est une procédure entière qui est chargée ou non.
:::

L'analogie s'arrête sur un point : le cuisinier connaît le plat commandé, l'agent choisit d'après la seule description. Si elle est floue, la skill n'est jamais ouverte.

Anthropic a présenté les Agent Skills en octobre 2025, puis les a publiées comme standard ouvert le 18 décembre 2025. En septembre 2026, le site du standard recense une quarantaine d'outils compatibles, et Lovable a adopté le format le 18 mai 2026. Une skill bien écrite voyage donc : chaque outil ajoute ses options, mais le nom, la description et les instructions restent les mêmes partout (les autres outils sont évoqués en annexe H). Comme elle peut contenir des scripts qui s'exécutent avec vos droits, n'installez une skill trouvée en ligne qu'après avoir lu son SKILL.md et appliqué la check-list « Avant d'installer une skill ou un serveur MCP » de l'annexe B.

### Dans Claude : Paramètres, Compétences

Le chapitre 4 a fait le tour de cette page et de ses deux onglets, captures à l'appui. Un seul prérequis à rappeler : dans les Paramètres, la rubrique Capacités doit autoriser l'exécution de code et la création de fichiers, sans quoi aucune compétence ne fonctionne.

Les compétences de documents d'Anthropic (Word, Excel, PowerPoint, PDF) s'appliquent d'office. Pour les autres, laissez Claude choisir d'après la description, ou nommez-la (« utilise la compétence relecture-manuel »).

:::notice Installer une compétence personnelle dans Claude
1. Ouvrez Paramètres, puis Capacités, et vérifiez que l'exécution de code et la création de fichiers est activée.
2. Nommez le dossier de la compétence exactement comme son champ name.
3. Compressez ce dossier en zip, le dossier lui-même à la racine de l'archive.
4. Ouvrez Paramètres, puis Compétences, cliquez sur « Ajouter » et choisissez le zip.
5. Ouvrez une conversation neuve et formulez une demande qui correspond à la description, sans nommer la compétence.
:::

:::attention Deux causes de refus à l'import
Claude refuse les champs d'en-tête hors standard : une option propre à Claude Code provoque l'erreur « Unexpected key » ; retirez la ligne avant de zipper. Quant à la description, le standard autorise 1 024 caractères, mais le centre d'aide de Claude indique 200 caractères pour un téléversement au moment où j'écris : restez sous 200.
:::

### Dans Claude Code : des dossiers et des commandes

Claude Code (chapitre 19) range les skills dans des dossiers ordinaires : ~/.claude/skills/<nom>/SKILL.md pour une skill personnelle, valable dans tous vos projets ; .claude/skills/<nom>/SKILL.md, à la racine du dépôt, pour une skill de projet, qui part avec le code sur GitHub. Les compétences de votre compte Claude sont synchronisées dans ~/.claude/skills/synced/.

Chaque skill devient une commande (/relecture-manuel), que Claude peut aussi déclencher seul. Claude Code ajoute au standard des options d'en-tête. disable-model-invocation: true réserve la skill à votre commande, ce qui convient à tout ce qui publie, déploie ou envoie. context: fork la fait travailler dans un sous-agent, avec son propre contexte. Ces options font échouer l'import dans Claude : si une skill doit servir partout, gardez l'en-tête minimal.

:::notice Installer une skill dans Claude Code
1. Ouvrez un terminal dans le dossier du dépôt du Guide.
2. Créez le dossier .claude/skills/relecture-manuel et déposez-y le SKILL.md.
3. Lancez une nouvelle session avec claude.
4. Tapez / et vérifiez que relecture-manuel apparaît dans la liste.
5. Faites un commit : la skill est désormais versionnée avec le livre.
:::

### Dans Lovable : des skills pour tout l'espace de travail

Les Skills de Lovable, lancées le 18 mai 2026, valent pour tous les projets de l'espace de travail. La Knowledge (chapitre 6) est toujours dans le contexte et dit ce qui est vrai en permanence (les cinq statuts d'un chapitre de L'Atelier) ; une skill est chargée à la demande et dit comment faire une chose précise, par exemple ajouter une page d'administration conforme au reste de l'application.

Lovable fournit des skills en lecture seule (contrôle d'accessibilité, refonte graphique, revue SEO, création vidéo, skill-creator, et Goal, qui travaille seul jusqu'à un objectif en consommant nettement plus de crédits). Pour les vôtres : /skill-creator dans le chat (payant en crédits), l'écriture à la main, l'import d'un dépôt GitHub, le téléversement d'un zip ou d'un fichier .skill de 50 Mo au plus, ou l'enregistrement depuis une conversation réussie.

:::notice Ajouter une skill à la main dans Lovable
1. Vérifiez que vous êtes propriétaire ou administrateur de l'espace : les éditeurs utilisent les skills mais n'en créent pas.
2. Ouvrez Settings, puis Skills, puis Add.
3. Donnez un nom de 1 à 64 caractères, en minuscules, chiffres et tirets.
4. Rédigez une description qui commence par « Use when… ».
5. Collez les instructions en Markdown et enregistrez.
6. Dans un projet, tapez / dans le chat pour vérifier que la skill apparaît.
:::

L'ajout par les réglages est gratuit ; l'usage d'une skill ne coûte que le prix du message.

:::astuce Transformer une réussite en skill
Quand une demande a enfin donné exactement ce que vous vouliez (la page de gestion des relecteurs de L'Atelier, avec ses droits, ses messages d'erreur en français et son bouton grisé pendant l'envoi), écrivez dans le chat de Lovable « save that as a skill » avant de passer à autre chose. Relisez ce que Lovable a rédigé et corrigez la description : la prochaine page d'administration ne vous coûtera pas les mêmes allers-retours.
:::

### Les skills utiles pour débuter

Inutile d'en installer trente : chaque skill ajoute sa description à la liste que l'agent parcourt. Chez Anthropic, skill-creator guide l'écriture d'une skill et sait l'évaluer : c'est la première à activer. frontend-design, parmi les plus installées de l'écosystème (917 000 installations selon l'annuaire skills.sh en septembre 2026), vise des interfaces soignées qui évitent l'allure « IA générique », ce qui sert le site vitrine du Guide. Dans Lovable, la revue SEO et le contrôle d'accessibilité s'appliquent directement à ce même site (chapitre 12). Et il y a grill-me, de Matt Pocock, que je vous recommande avant toute nouvelle fonctionnalité.

### Les skills de Matt Pocock

Le lot de skills sans doute le plus célèbre de l'écosystème porte ce sous-titre : « My agent skills that I use every day to do real engineering - not vibe coding ». Des skills pour faire de la vraie ingénierie, pas du vibe coding. L'ironie est savoureuse dans un livre qui porte ce mot dans son titre, et instructive : ce dépôt apporte ce qui manque au vibe coding naïf, une discipline glissée dans le flux de travail.

Matt Pocock, ancien professeur de chant devenu formateur de référence sur TypeScript, défend une conviction : un code produit plus vite rend le jugement humain plus nécessaire, pas moins. Il conseille de concevoir un projet comme si un collègue se réveillait chaque matin sans souvenir de la veille, ce qui est la situation d'un agent. Son dépôt, github.com/mattpocock/skills, est sous licence MIT et réunit des skills petites, faciles à adapter et à combiner.

:::fiche GRILLING · MÉTHODE
**Définition.** Chez Matt Pocock, le fait de se faire interroger sans relâche par l'agent sur un plan, jusqu'à ce que chaque choix soit tranché.

**Analogie.** Le grand oral devant un jury tenace, avant d'ouvrir le chantier.

**À ne pas confondre avec.** Le brainstorming du chapitre 9, qui ouvre des pistes ; le grilling les ferme une à une.
:::

**Installer avec ou sans terminal**

Le README propose deux chemins, à ne pas cumuler sous peine de doublons. Dans Claude Code, /plugin install mattpocock-skills installe un plugin qui se met à jour seul mais ne se modifie pas ; npx skills@latest add mattpocock/skills (Node.js requis) copie les skills choisies, modifiables mais sans mise à jour. On lance ensuite /setup-matt-pocock-skills une fois par projet : il demande où ranger les tickets (de simples fichiers locaux suffisent pour débuter) et les documents produits.

Sans terminal, ces skills fonctionnent aussi, puisqu'elles suivent le standard : skills/engineering/ pour la fabrication, skills/productivity/ pour grill-me et ses voisines.

:::notice Importer grill-me dans Lovable
1. Ouvrez Settings, puis Skills, et choisissez l'import depuis GitHub.
2. Indiquez le dépôt mattpocock/skills, sous-dossier skills/productivity.
3. Vérifiez que la liste importée contient grill-me et grilling.
4. Dans le projet L'Atelier, tapez /grill-me suivi de la fonctionnalité à discuter, en deux phrases.
:::

Dans Claude, la voie est le zip : isolez les dossiers grill-me et grilling de l'archive du dépôt, gardez dans chaque en-tête name et description seulement, zippez-les séparément et ajoutez-les depuis la page Compétences.

:::attention Le piège de grill-me
Le SKILL.md de grill-me se réduit à une ligne : il appelle une autre skill, grilling, qui contient la vraie technique d'interrogatoire. Importée seule, grill-me ne sait rien faire. Même logique ailleurs : grill-with-docs s'appuie aussi sur grilling, et implement appelle tdd puis code-review. Avant d'importer une skill de ce dépôt, repérez les noms que cite son SKILL.md.
:::

**Six skills commentées**

Le dépôt en compte plus de vingt-cinq ; six suffisent pour comprendre la méthode (noms de septembre 2026 ; la liste complète et la table des anciens noms, comme write-a-prd ou diagnose, sont en annexe F).

grill-me vous interroge sur un plan, une question à la fois, jusqu'à ce que chaque branche soit tranchée, sans rien écrire dans le projet. Elle ne demande aucune connaissance technique (1,2 million d'installations selon skills.sh en septembre 2026).

grill-with-docs mène le même interrogatoire dans un projet existant, en consignant le vocabulaire du métier et les décisions d'architecture dans un fichier CONTEXT.md : pour L'Atelier, « relecteur bêta » ou « statut Relecture » y reçoivent une définition unique.

to-spec transforme la conversation en spécification sans poser de question : elle ne fait que synthétiser l'interrogatoire qui précède. to-tickets découpe ensuite la spécification en tickets par tranches verticales : chaque ticket traverse l'application de l'écran jusqu'à la base de données et indique ce qui le bloque.

implement construit ce que décrit un ticket, en développant par les tests (tdd) et en finissant par une relecture (code-review) des normes du dépôt et de la fidélité au ticket. diagnosing-bugs, enfin, mène une chasse méthodique quand quelque chose casse (reproduire, réduire, faire des hypothèses, corriger, ajouter un test) : c'est la version outillée de la démarche du chapitre 18.

**L'enchaînement, appliqué au SaaS**

Prenons une fonctionnalité du SaaS « Audit Vibe Coding » (chapitre 22) : l'envoi au client d'un rapport d'audit relu, avec une offre de conseil en fin de rapport.

- /grill-with-docs : l'agent vous interroge. Qui relit le rapport avant l'envoi ? Que reçoit un client dont l'abonnement a expiré ? Que faire si le dépôt GitHub fourni est privé ?

- Si le travail dépasse une session : /to-spec, puis /to-tickets. Sinon, on passe à l'étape 3.

- /implement, ticket par ticket, avec /clear entre deux tickets pour repartir d'un contexte propre.

- Quand quelque chose casse : /diagnosing-bugs.

Deux règles d'hygiène accompagnent ce flux : garder les deux premières étapes dans une seule conversation, pour que la spec hérite de l'interrogatoire, et rester dans ce que Pocock appelle la « smart zone », environ 150 000 tokens, au-delà desquels le modèle raisonne moins bien. Pour une tâche triviale, grill-me pose trop de questions : on s'en passe.

:::mot Le paradoxe de l'interrogatoire
On attend d'un assistant qu'il réponde. La skill la plus populaire de ce dépôt fait l'inverse : elle questionne.

Une idée d'application ressemble à un arbre dont chaque choix (payant ou gratuit, avec ou sans compte, relu ou envoyé tel quel) ouvre des branches. Quand vous la décrivez en trois phrases, vous parcourez une seule branche, celle qui vous plaît. L'agent comble les autres au hasard, et c'est de là que viennent tant d'applications « presque justes ». Quelques minutes de questions gênantes coûtent moins cher que des jours de corrections.
:::

### Écrire sa propre skill

Écrire une skill est un exercice de rédaction, pas de programmation : expliquer une procédure à quelqu'un de très compétent qui ignore tout de votre métier, comme un mode opératoire pour un stagiaire.

L'en-tête du SKILL.md est encadré de deux lignes de trois tirets simples et contient deux champs obligatoires. Le name : 64 caractères au plus, en minuscules, chiffres et tirets, identique au nom du dossier. La description : ce que fait la skill et quand l'utiliser, avec les mots que vous employez vous-même. C'est le seul texte que l'agent lit avant de décider. « Aide pour les chapitres » ne déclenchera presque rien ; « relit un chapitre selon la charte ; à utiliser pour relire, corriger ou vérifier un chapitre » sera reconnue. Viennent ensuite les instructions : des étapes, un exemple du résultat attendu, les cas limites. La spécification conseille de rester sous 500 lignes et de placer les longs documents dans des fichiers annexes.

**Un exemple complet : relecture-manuel**

Le chapitre 5 a lancé l'ébauche de relecture-manuel avec skill-creator. Voici une version complète, à comparer avec la vôtre plutôt qu'à recopier. Elle ne réécrit rien d'office : elle rend un rapport classé par gravité. Le dossier contient le SKILL.md et un fichier annexe facultatif, references/mots-proscrits.md.

```text
---
name: relecture-manuel
description: Relit un chapitre de Le Guide du Vibe Coding selon la charte : voix, mots proscrits, balisage, faits datés, renvois. À utiliser pour relire, corriger ou vérifier un chapitre.
---
 
# Relecture d'un chapitre du Guide
 
Tu relis un chapitre de « Le Guide du Vibe Coding », guide en français
pour des lecteurs qui n'ont jamais codé. Tu es un relecteur exigeant,
pas un réécrivain. Tu ne modifies rien sans accord.
 
## Étape 1 : la voix
- Le lecteur est vouvoyé. L'auteur dit « je » (convictions, choix)
  et « nous » (l'auteur et le lecteur qui construisent ensemble).
- Signale toute anecdote ou tout résultat personnel prêté à l'auteur.
- Signale les chutes en slogan et les séries de trois forcées.
- « vibe coding » en deux mots, « vibecodeur » pour la personne.
 
## Étape 2 : les interdits mécaniques
- Aucun tiret cadratin ni demi-cadratin. Cite chaque ligne fautive.
- Mots proscrits : voir references/mots-proscrits.md. À défaut :
  crucial, incontournable, véritable, révolutionnaire, levier.
- Pas d'URL dans le texte courant, sauf blocs de code et annexe I.
 
## Étape 3 : les faits
- Chaque chiffre, prix, date ou citation doit être daté et venir des
  notes de recherche fournies. Sinon, signale-le.
- Un fait marqué [À VÉRIFIER] ne doit jamais être présenté comme sûr.
 
## Étape 4 : le balisage et les renvois
- Encadrés : « ::: type Titre », contenu, puis « ::: » seul sur sa ligne.
  Types admis : mot, klein, etapes, prompt, attention, astuce, cout,
  checklist, resume. Aucun tableau dans un encadré.
- Le chapitre finit par un encadré resume.
- Chaque « chapitre N » doit viser le bon chapitre ; en cas de doute,
  pose la question.
 
## Rendu
1. Trois niveaux : Bloquant (fait faux, anecdote inventée, balisage
   cassé), Important (voix, mots proscrits, tirets), Confort (rythme).
2. Pour chaque point : la citation exacte, le problème, une proposition.
3. Au plus 25 points ; s'il y en a davantage, les 25 plus graves et
   le nombre total.
4. Termine par : « Voulez-vous que j'applique les corrections
   bloquantes et importantes ? »
```

La description reste sous 200 caractères et reprend les verbes de l'auteur. La première phrase fixe un rôle et une limite. Le fichier annexe n'est lu que si besoin. Le rendu impose une forme contrôlable et un plafond de 25 points, parce qu'un rapport de deux cents remarques ne sera jamais lu. L'en-tête ne contient que des champs standard : la skill s'importe telle quelle dans les trois outils.

:::astuce La même consigne, trois usages
Ce texte sert comme compétence dans Claude, pour une relecture ponctuelle, et comme skill de projet dans le dépôt du livre, pour Claude Code. Sa grille peut aussi servir de consigne système à la fonction relire-chapitre de L'Atelier (chapitre 16), réservée à l'auteur, à deux conditions : retirer la question finale, puisque la fonction ne converse pas, et ramener le rendu à dix points, pour rester près des 1 500 tokens de sortie sur lesquels repose le calcul de coût du chapitre 16.
:::

:::notice Tester votre skill
1. Installez relecture-manuel dans l'outil de votre choix.
2. Ouvrez une conversation neuve, collez un chapitre et écrivez, sans nommer la skill : « Peux-tu relire ce chapitre ? »
3. Vérifiez que le rapport suit les trois niveaux au lieu d'une réécriture complète.
4. Si rien ne se déclenche, ajoutez à la description les mots que vous venez d'employer.
5. Faites un essai avec une demande sans rapport, une recette de cuisine par exemple, pour vérifier que la skill reste muette.
6. Glissez volontairement un tiret cadratin et un « crucial » dans un paragraphe, et vérifiez qu'ils sont relevés.
:::

Le dernier point applique à un outil de relecture le principe de la recette du chapitre 18 : une skill qui ne trouve pas une faute placée exprès ne trouvera pas les autres.

Pour les suivantes, demandez à skill-creator de vous interroger puis de rédiger, avec les mêmes contraintes, et relisez toujours le résultat : une skill non lue se déclenchera en votre nom sans que vous en connaissiez le détail.

### Les hooks : ce qui doit arriver à chaque fois

Une skill reste une consigne ; le modèle la suit, en général. La documentation de Claude Code le dit à propos du fichier CLAUDE.md : c'est du contexte, pas une configuration imposée. L'incident de Replit, raconté au chapitre 20, en est l'illustration : la consigne de gel existait, rien ne l'imposait.

Les hooks comblent ce manque. Ce sont des commandes que Claude Code exécute lui-même à des moments précis : avant qu'un outil agisse (PreToolUse), après une action (PostToolUse), quand l'agent attend votre réponse (Notification), quand il a fini de répondre (Stop). Ils se déclenchent à chaque fois, sans dépendre du bon vouloir du modèle. Un vibecodeur s'en sert surtout pour bloquer une commande dangereuse, remettre le code en forme après chaque modification ou être prévenu quand Claude attend une réponse.

:::fiche HOOK · SÉCURITÉ
**Définition.** Une commande que Claude Code exécute automatiquement à un moment précis du travail de l'agent (avant ou après une action, à la fin d'une réponse), sans que le modèle puisse s'y soustraire.

**Analogie.** Le disjoncteur du tableau électrique : il coupe sans demander l'avis de l'appareil.

**À ne pas confondre avec.** Un webhook, message qu'un service extérieur envoie à votre application ; ni une skill, que le modèle suit s'il la juge pertinente.
:::

On configure les hooks dans un fichier de réglages (settings.json, pour vous ou pour le projet) : demandez la configuration à Claude, relisez-la, puis tapez /hooks pour voir ceux qui sont actifs. Matt Pocock fournit un exemple prêt à l'emploi, git-guardrails-claude-code, rangé à part dans le dossier misc de son dépôt : des hooks qui bloquent git push, git reset --hard ou git clean, les commandes qui publient ou effacent sans retour.

:::prompt Un hook pour la charte du livre
Écris-moi un hook Claude Code pour ce projet, dans le fichier de réglages du projet. Événement : PostToolUse, sur les outils Edit et Write. Action : si le fichier modifié se termine par .md, chercher les tirets cadratins et demi-cadratins ; s'il y en a, afficher les numéros de ligne et demander à l'agent de les remplacer.

Explique-moi chaque ligne de la configuration avant de l'écrire, puis dis-moi comment vérifier avec /hooks qu'il est actif.
:::

La skill juge (le ton, les faits, la voix) quand on la sollicite ; le hook vérifie sans exception ce qui se vérifie mécaniquement. Un hook reste une commande lancée sur votre machine, avec vos droits : lisez-le, et ne copiez jamais la configuration d'un inconnu. Dans Lovable et dans Claude, aucun mécanisme équivalent n'est documenté au moment où j'écris ; pour les gestes irréversibles, la protection reste humaine, avec le mode Plan, les versions et les réflexes du chapitre 7.

:::bref Une skill est un dossier avec un SKILL.md (nom, description, instructions), chargé seulement quand la demande correspond à sa description : c'est la divulgation progressive.
Claude : Paramètres, Capacités, puis Compétences. Claude Code : .claude/skills/ dans le dépôt. Lovable : Settings, Skills, pour tout l'espace de travail.

Les skills de Matt Pocock apportent de la discipline : grill-me (toujours avec grilling), grill-with-docs, to-spec, to-tickets, implement, diagnosing-bugs ; liste complète en annexe F.

Écrire une skill est un exercice de rédaction : une description avec vos mots, des étapes, une forme de rendu, un test avec une faute volontaire.

Une skill conseille, un hook impose : pour ce qui ne souffre pas d'exception, il faut un hook dans Claude Code.
:::
