*Où nous installons à Claude Code un navigateur qu'il pilote lui-même, pour qu'il teste nos sites et nos applications comme le ferait un visiteur exigeant. Et où chaque bug trouvé devient un garde-fou permanent.*

### L'écrivain qui ne se relit pas

Vous connaissez sans doute cette expérience. On écrit une page, on la relit, on la trouve impeccable. Le lendemain, un ami la lit et trébuche dès la deuxième ligne sur une répétition que nous n'avions pas vue. Ce n'est pas de la négligence : notre cerveau lit ce que nous avons voulu écrire, pas ce que nous avons écrit. Il corrige en silence, et cette correction silencieuse nous rend aveugles.

Un agent qui code sans voir le résultat est exactement dans cette situation, avec une circonstance aggravante : il n'a même pas de lendemain. Il écrit le composant, il est convaincu que le bouton s'affiche, il vous annonce que c'est terminé. Et c'est vous qui découvrez, sur votre téléphone, que le bouton déborde de l'écran.

Au chapitre précédent, nous avons retenu de Boris Cherny qu'un agent doit pouvoir vérifier son propre travail. Ce chapitre donne à Claude l'outil de vérification le plus parlant qui soit : un navigateur qu'il pilote lui-même. Il ouvre la page, clique, remplit les formulaires, change la taille de l'écran, lit la console, prend des captures, et vous rend un rapport. Il devient le lecteur du lendemain.

L'idée m'est venue d'une vidéo de Shubham Sharma, créateur francophone qui publie régulièrement des tutoriels sur Claude Code, et qui y montre comment il installe Playwright pour faire tester ses sites en direct. Je vous recommande de la regarder, ainsi que la page de ressources qui l'accompagne. Ce chapitre n'en est pas la transcription : nous allons construire notre propre méthode, adaptée aux projets de ce livre, avec notre propre recette de test.

### Qu'est-ce que Playwright ?

Playwright est un outil libre, maintenu par Microsoft, qui permet à un programme de piloter un vrai navigateur : Chromium (la base de Chrome et d'Edge), Firefox ou WebKit (la base de Safari). Il est né pour les tests automatisés, c'est-à-dire pour que des développeurs puissent écrire une fois pour toutes des scénarios du type « ouvre la page de connexion, saisis ces identifiants, vérifie que le tableau de bord s'affiche », puis les rejouer à chaque modification.

Ce qui a changé récemment, c'est que Playwright s'est doté d'une interface pensée pour les agents. Plutôt que d'écrire du code de test, l'agent envoie des commandes simples, une à une : ouvre cette adresse, décris-moi la page, clique sur tel élément, prends une capture. Et l'équipe de Playwright fournit une compétence (skill) officielle qui apprend à Claude Code à se servir de ces commandes. Nous retrouvons ici le mécanisme découvert au chapitre 4 : une compétence est un mode d'emploi que Claude lit au moment où il en a besoin.

Le point décisif pour nous, c'est la façon dont l'agent « voit » la page. Il ne regarde pas une image de l'écran pixel par pixel. Il reçoit une description structurée de la page, ce qu'on appelle l'arbre d'accessibilité : la liste des titres, des boutons, des champs, des liens, avec leur texte et leur rôle. C'est la même description que lit un logiciel de synthèse vocale pour une personne aveugle. Il y a là une belle symétrie : un site bien construit pour l'accessibilité est aussi un site que l'agent comprend bien. Et quand l'agent a besoin de voir vraiment, il prend une capture d'écran et la regarde.

### Trois façons de donner un navigateur à Claude

Avant d'installer quoi que ce soit, situons Playwright parmi ses cousins. Car vous avez peut-être déjà vu Claude utiliser un navigateur, et la confusion est fréquente.

```text
Claude in Chrome, Playwright MCP ou Playwright CLI ?
Claude in Chrome : l'extension qui laisse Claude agir dans votre propre Chrome, avec vos sessions ouvertes. Idéale pour une vérification ponctuelle, une démarche en ligne, un site où vous êtes connecté. C'est l'outil que nous utilisons pour les captures de ce livre. Inconvénient : c'est votre navigateur, avec vos comptes ; on ne le lâche pas en autonomie sur une longue série de tests.
Playwright par MCP : un serveur MCP (chapitre 4) qui expose le navigateur à Claude sous forme d'outils. Simple à brancher, mais chaque page visitée remplit la conversation de descriptions volumineuses.
Playwright CLI avec sa compétence : Claude pilote le navigateur par des commandes courtes dans le terminal et ne lit que ce dont il a besoin. C'est l'option la plus économe en contexte, donc la plus adaptée aux longues séances de test. C'est celle que nous installons.
En résumé : Chrome pour agir en votre nom, Playwright pour tester en toute indépendance, dans un navigateur neuf, jetable et reproductible.
```

### Installation : dix minutes, une fois pour toutes

Les commandes ci-dessous sont celles de la documentation officielle de Playwright au moment où j'écris. Elles évoluent ; vérifiez-les sur le site de Playwright avant de les taper. Il vous faut Node.js en version 20 ou plus, que Lovable et Claude Code vous ont probablement déjà fait installer.

```text
# 1. Installer l'outil en ligne de commande, pour tout l'ordinateur
npm install -g @playwright/cli@latest
 
# 2. Dans le dossier de votre projet : préparer l'espace de travail
#    et installer la compétence pour Claude Code
playwright-cli install
playwright-cli install --skills
 
# Variante : installer la compétence pour tous vos projets
playwright-cli install --skills -g
 
# 3. (Si besoin) installer explicitement les navigateurs
playwright-cli install-browser
```

La deuxième commande dépose la compétence dans le dossier .claude/skills du projet. Désormais, dès que vous demandez à Claude Code de tester une page, il sait qu'il dispose de cet outil et comment s'en servir. Vous n'avez pas besoin d'apprendre les commandes de Playwright : c'est précisément le travail de la compétence.

Et plutôt que de taper vous-même ces lignes, vous pouvez appliquer le principe du chapitre précédent : demandez à Claude Code de les exécuter, de vérifier que tout fonctionne, et de vous dire ce qu'il a fait. Premier test, pour s'assurer que la mécanique tourne :

```text
Séance
Moi : Ouvre la page d'accueil du site du livre, dans un navigateur visible, et décris-moi ce que tu vois : titre, boutons, liens du menu. Ne clique sur rien.
Claude : [il ouvre le navigateur, lit la page] La page s'ouvre sur le titre « Le Guide du Vibe Coding ». Le menu contient cinq liens : Le livre, Les chapitres, L'auteur, Ressources, Acheter. Un bouton principal « Lire un extrait » est visible sans défiler. En bas de page, un formulaire d'inscription à la lettre d'information avec un champ e-mail.
```

Si Claude vous répond cela, votre installation fonctionne. Remarquez l'option « navigateur visible » : pendant les premières séances, regardez-le travailler. Voir le curseur se déplacer tout seul sur votre site a quelque chose de troublant, et c'est aussi le meilleur moyen de comprendre ce qu'il fait.

```text
Réflexe. Testez l'adresse publiée, pas l'éditeur
Pointez toujours Playwright vers l'adresse publiée de votre site ou vers une préversion, jamais vers l'éditeur de Lovable. Vous éviterez de consommer des crédits pour rien et, surtout, vous testerez ce que vos visiteurs voient réellement.
```

### La recette de l'inspecteur

Un navigateur piloté ne sert à rien sans une consigne claire. Demander « teste mon site » produit un test vague, qui s'arrête à la première page. Il faut dire à l'agent ce qu'il doit parcourir, ce qu'il doit contrôler, ce qu'il ne doit surtout pas faire, et sous quelle forme rendre son travail.

Voici la recette que j'utilise pour les projets de ce livre. Je l'ai construite comme un cahier des charges d'inspecteur, en cinq blocs. Conservez-la dans votre projet Claude (chapitre 5) ou transformez-la en compétence personnelle, et adaptez les parcours à chacune de vos applications.

```text
RECETTE DE L'INSPECTEUR (version 1)
 
1. MISSION
Tu es chargé de la recette de [NOM DU PROJET], publié à [ADRESSE].
Ton rôle est de constater, pas de corriger. Tu ne modifies aucun
fichier du projet pendant cette mission.
 
2. PARCOURS À SUIVRE
Reprends les parcours décrits dans le journal de décisions
(rubrique « Parcours utilisateurs »). Pour chacun : suis-le
jusqu'au bout, comme un visiteur pressé, puis comme un visiteur
distrait qui se trompe de champ ou revient en arrière.
 
3. CONTRÔLES À FAIRE SUR CHAQUE PAGE
- Console du navigateur : erreurs et avertissements.
- Trois largeurs d'écran : téléphone, tablette, ordinateur.
- Liens : chacun mène-t-il à une page existante ?
- Images : se chargent-elles, ont-elles un texte alternatif ?
- Formulaires : messages d'erreur clairs si un champ est vide
  ou mal rempli.
- Textes : fautes visibles, textes de démonstration oubliés.
 
4. INTERDITS
- Aucun paiement réel, aucun envoi à une vraie adresse e-mail.
- Uniquement les comptes de test fournis par variables
  d'environnement ; ne jamais afficher un mot de passe.
- Rester sur le domaine indiqué ; ne pas suivre les liens externes
  au-delà de la vérification qu'ils répondent.
 
5. LIVRABLE
Un rapport HTML autonome, rangé dans le dossier qa/ avec la date :
- une synthèse en cinq lignes ;
- un tableau des anomalies : page, description, gravité
  (bloquant, gênant, cosmétique), étapes pour reproduire ;
- une capture d'écran pour chaque anomalie ;
- la liste de ce qui a été vérifié et fonctionne.
```

Relisez les blocs 1 et 4 : ce sont eux qui font la différence. Le premier sépare le constat de la correction. Un inspecteur qui répare en passant brouille les pistes : on ne sait plus ce qui était cassé, ni si la réparation a créé autre chose. Le quatrième fixe les limites. Nous retrouvons la règle des trois zones du chapitre précédent : un test de lecture est en zone verte, mais un test qui soumet des formulaires sur un site en production touche la zone orange, et tout ce qui déclenche un paiement ou un envoi réel relève de la zone rouge.

Notez aussi la gradation de gravité. Elle a l'air d'un détail administratif ; elle est en réalité ce qui rend le rapport utilisable. Un rapport de quarante anomalies non classées décourage. Le même rapport avec deux bloquants en tête se lit en trente secondes et dit par où commencer.

### Mise en pratique sur le site du livre

Premier terrain d'essai, le site vitrine de l'axe 1. Je lance la recette sur la version publiée. Vingt minutes plus tard, le rapport est dans le dossier qa/. Il signale trois choses : un lien du pied de page vers les mentions légales qui mène à une page introuvable, un bouton « Acheter » qui passe sous le bandeau des cookies sur un écran de téléphone, et une image de couverture sans texte alternatif. Rien de dramatique, mais trois défauts que je n'avais pas vus, parce que je consulte mon site sur mon ordinateur, connecté, en sachant déjà où cliquer. Exactement l'aveuglement de l'écrivain qui se relit.

Je demande ensuite à Claude Code, dans une autre séance et en mode plan, de proposer les corrections. Il les applique, je synchronise avec Lovable, puis je relance la recette. Le rapport revient vide de bloquants. Ce va-et-vient entre un inspecteur qui ne corrige pas et un artisan qui ne s'inspecte pas est la structure la plus saine que je connaisse. C'est d'ailleurs ainsi que fonctionnent les laboratoires : celui qui fait la mesure n'est pas celui qui a construit l'appareil.

### Mise en pratique sur Audit Vibe Coding : tester ce qui ne se voit pas

Sur un site vitrine, les défauts se voient. Sur un SaaS, les plus graves ne se voient pas. Souvenez-vous du chapitre précédent : Claude a repéré dans le code une politique d'accès trop large sur les rapports d'audit, et nous l'avons corrigée avec un test. Playwright permet d'aller plus loin et de vérifier la même chose de l'extérieur, comme le ferait un utilisateur malveillant.

La consigne est simple à formuler. Deux comptes de test, A et B. Avec le compte A, créer un rapport d'audit et noter son adresse. Se déconnecter, se connecter avec le compte B, et tenter d'ouvrir directement l'adresse du rapport de A. Le résultat attendu est un refus. Tout autre résultat est un bloquant.

C'est précisément le scénario de la faille BOLA racontée au chapitre 20 : un objet accessible à quiconque connaît son identifiant. Un humain pense rarement à faire ce test, parce qu'il faut jongler entre deux comptes et deviner les adresses. Un agent le fait sans se lasser, sur chaque type d'objet de l'application : rapports, factures, projets, paramètres.

```text
Attention. Les identifiants de test
Ne collez jamais un mot de passe dans une consigne. Créez des comptes dédiés aux tests, sans aucune donnée réelle, et placez leurs identifiants dans des variables d'environnement que Claude lit sans les afficher. Et ne pointez Playwright que vers des sites qui vous appartiennent : tester le site d'un tiers sans autorisation peut poser un problème juridique, même avec les meilleures intentions.
```

### De l'inspection au garde-fou permanent

Jusqu'ici, Claude pilote le navigateur à la main, pour ainsi dire : il découvre la page et décide de ses gestes en direct. C'est parfait pour explorer, mais ce n'est pas reproductible à l'identique. La dernière étape consiste à transformer chaque anomalie corrigée en un test écrit, que Playwright rejouera tout seul à chaque modification.

La consigne tient en une phrase : « Pour chaque anomalie bloquante du dernier rapport, écris un test Playwright qui l'aurait détectée, vérifie qu'il passe sur la version corrigée, et range-le dans le dossier des tests. » Claude écrit alors de vrais fichiers de test, que l'on lance d'une seule commande. Le test d'isolation entre les comptes A et B devient une sentinelle permanente. Si demain une modification dans Lovable rouvre la faille, le test échoue avant que vos clients ne s'en aperçoivent.

C'est ainsi que la qualité s'accumule. Un rapport d'inspection est une photographie ; une suite de tests est une mémoire. Nous retrouvons l'idée du fichier CLAUDE.md et de sa rubrique « Erreurs déjà commises » : chaque bug trouvé une fois doit devenir impossible à reproduire en silence.

```text
Réflexe. Le rythme de recette
À chaque modification importante : relancer la suite de tests écrits (quelques minutes).
Avant chaque mise en ligne : relancer la recette complète de l'inspecteur (vingt à quarante minutes).
Chaque mois : faire lire le rapport par Claude, en lui demandant quelles familles d'anomalies reviennent, et ce qu'il faudrait ajouter au journal de décisions pour les prévenir.
```

### Un cadeau inattendu : la vidéo de la séance

Playwright sait enregistrer en vidéo ce qu'il fait dans le navigateur. On l'utilise d'abord pour comprendre un bug : on revoit la séquence exacte qui a mené à l'erreur. Mais j'ai vite remarqué autre chose. Une séance de test bien menée, c'est aussi une démonstration propre de votre application : pas d'hésitation du curseur, pas de faute de frappe, pas de notification intempestive, et pas de visage à l'écran.

Autrement dit, la vidéo d'une recette est un rush tout prêt pour un tutoriel. Nous allons nous en servir au chapitre suivant, consacré au montage vidéo avec Claude.

*Planche 31. L'inspecteur et l'artisan, notice de montage de la boucle de test*

```text
Carnet de bord
Installez Playwright et sa compétence dans le dossier d'un de vos projets. Faites décrire la page d'accueil par Claude, sans clic.
Adaptez la recette de l'inspecteur à ce projet : écrivez vos parcours dans le journal de décisions, puis lancez une première recette sur l'adresse publiée.
Choisissez l'anomalie la plus grave du rapport et demandez-en le test de non-régression.
```
