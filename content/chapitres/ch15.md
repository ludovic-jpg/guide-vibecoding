Au premier message du lot 1, quelque chose d'invisible se produit. Vous demandez un tableau de chapitres que l'auteur peut créer et modifier ; Lovable comprend qu'il faut les retenir quelque part, et active Lovable Cloud de lui-même, comme il le fait par défaut quand une demande exige un serveur. En quelques secondes, votre projet a acquis une base de données PostgreSQL, un système de comptes, un espace de fichiers et un endroit où exécuter du code côté serveur.

C'est confortable, et c'est le moment où l'on cesse de regarder. L'Atelier ne le permet pas : tout ce que le chapitre 14 a décidé sur le papier (qui voit quoi) va s'écrire ici, dans des règles que l'interface ne montre pas. Tables, comptes, rôles, règles d'accès, fichiers, fonctions serveur, secrets et coûts : la sécurité pour elle-même attendra le chapitre 20, la sortie de Cloud le chapitre 19.

:::mot Politique, un mot de la cité
Dans le vocabulaire de Supabase, sur lequel repose Lovable Cloud, une règle d'accès s'appelle une *policy*, que les traductions automatiques rendent par « politique ». « La politique de la table commentaires » fait sourire.

Le rapprochement est pourtant moins absurde qu'il n'y paraît. *Policy* et « politique » descendent tous deux du grec *polis*, la cité. La politique, au sens premier, organise la vie commune : qui entre où, qui voit quoi. Une *policy* fait cela à l'échelle d'une table.

L'analogie s'arrête là, et c'est heureux. Une politique humaine se négocie et s'interprète. Une *policy* ne s'interprète pas : la base l'applique à chaque ligne, à chaque requête. Ce qu'elle n'autorise pas explicitement est refusé.
:::

### Faire le tour du propriétaire

Le tableau de bord de Cloud s'ouvre par *More*, puis *Cloud*. En septembre 2026, il compte onze onglets, dont six serviront chaque semaine : Database (les chapitres), Users (les relecteurs), Storage (les captures), Secrets (la clé Anthropic), Logs (les pannes), Usage (la facture).

Une décision ne se reprend jamais : la région. Cloud en propose trois (Amériques, Europe, Asie-Pacifique), choisit par défaut la plus proche, et un projet ne se déplace pas ensuite. Vérifiez que c'est l'Europe ; cela fixe où dorment les données, sans suffire au RGPD (chapitre 26).

### Les tables, par des migrations

Les tables du chapitre 14 ne se créent pas à la main. On les demande à Lovable, qui écrit une migration (un petit fichier SQL horodaté qui décrit le changement de structure), la fait relire (*reviewed migrations*) puis l'applique. Ces fichiers s'accumulent dans le dossier supabase/migrations/ du dépôt GitHub, qui contient ainsi la structure de la base, jamais ses données.

Pour le lot 1, une seule table suffit. Lovable produit à peu près ceci, qu'il vaut la peine de savoir lire :

```text
-- EXEMPLE À ADAPTER : relu et appliqué par Lovable sous forme de migration
create type public.statut_chapitre as enum
  ('idee', 'brouillon', 'redaction', 'relecture', 'publie');
 
create table public.chapitres (
  id uuid primary key default gen_random_uuid(),
  numero int not null,
  titre text not null,
  statut public.statut_chapitre not null default 'idee',
  contenu text,
  auteur_id uuid not null references auth.users,
  updated_at timestamptz not null default now()
);
```

La première instruction crée une liste fermée de statuts : la base refusera « en relecture » ou « Relu ». La colonne auteur_id est une clé étrangère vers la table des comptes, que Cloud gère sous le nom auth.users.

La vue Database affiche la table et l'exporte en CSV ; l'éditeur SQL interroge les données sans dépenser de crédit (select statut, count(*) from chapitres group by statut;).

:::attention Lire, pas écrire, dans l'éditeur SQL
Tenez-vous aux requêtes select. Un update ou un delete tapé dans l'éditeur ne passe par aucune relecture et ne laisse aucune trace dans le dépôt. Pour changer une structure ou corriger des données en masse, passez par Lovable, en mode Plan d'abord.
:::

### Les comptes : un outil sur invitation

L'authentification de Cloud propose par défaut l'e-mail et le mot de passe, et en option le téléphone par SMS, Google, Apple, Microsoft ou le SSO d'entreprise. Pour une dizaine de relecteurs, l'e-mail suffit.

Le réglage qui compte le plus pour L'Atelier est aussi le plus simple : fermer les inscriptions. Un outil interne n'a aucune raison de laisser un inconnu se créer un compte, même si ce compte ne verrait rien. Les relecteurs sont invités depuis la vue Users, qui permet de chercher, d'inviter et de supprimer un utilisateur. L'invitation part par e-mail, et Cloud sait envoyer ses e-mails depuis votre propre domaine, dans des plafonds relevés au chapitre 13 (50 000 par mois sur les offres payantes, 100 e-mails d'application par heure au plus sur l'offre Pro, en septembre 2026) : largement de quoi inviter une dizaine de relecteurs.

:::checklist Les comptes de L'Atelier
☐  Les inscriptions libres sont fermées ; les relecteurs sont invités depuis Users.

☐  La confirmation automatique des adresses, pratique en développement, est désactivée.

☐  La longueur minimale du mot de passe est d'au moins 8 caractères (6 par défaut).

☐  Le contrôle HIBP, qui refuse les mots de passe apparus dans des fuites connues, est activé.

☐  Les adresses de redirection après connexion ne contiennent que les domaines de L'Atelier.

☐  J'ai trois comptes de test : un auteur, deux relecteurs.
:::

### Les rôles, dans une table à part

Le chapitre 14 a rangé les rôles dans leur propre table, roles_utilisateurs, pour une raison concrète. Un relecteur a le droit de modifier son nom affiché dans profils. Si son rôle était une colonne de profils, la même règle lui permettrait, par une requête écrite à la main, de changer « relecteur » en « auteur ». Une table où seul l'auteur peut écrire ferme cette porte.

Reste à interroger cette table depuis les règles des autres tables. On le fait par une petite fonction, qui répond oui ou non à la question « la personne connectée a-t-elle tel rôle ? ».

```text
-- EXEMPLE À ADAPTER : rôles et fonction de vérification
create type public.role_atelier as enum ('auteur', 'relecteur');
 
create table public.roles_utilisateurs (
  user_id uuid not null references auth.users on delete cascade,
  role public.role_atelier not null,
  primary key (user_id, role)
);
alter table public.roles_utilisateurs enable row level security;
 
create function public.a_le_role(_role public.role_atelier)
returns boolean
language sql stable security definer set search_path = public
as $$
  select exists (
    select 1 from public.roles_utilisateurs
    where user_id = auth.uid() and role = _role
  );
$$;
```

Le mot à retenir est security definer : la fonction s'exécute avec les droits de celui qui l'a créée, non de celui qui l'appelle. Elle lit donc la table des rôles même quand la personne connectée n'y a pas accès, et ne renvoie qu'un oui ou un non. Mal écrite, elle contournerait toutes les règles : gardez-la courte, et faites-la relire.

### Les règles d'accès : d'abord en français

La sécurité au niveau des lignes (RLS, pour *Row Level Security*) est le mécanisme par lequel la base elle-même filtre, à chaque requête, les lignes qu'une personne a le droit de voir ou de modifier. Le chapitre 20 raconte ce qui arrive quand elle manque ; ici, nous l'écrivons.

La méthode ne varie pas : écrire chaque règle en français, table par table et opération par opération, la faire traduire en SQL, puis faire retraduire le SQL en français par une autre conversation pour vérifier que l'aller et le retour concordent. Pour L'Atelier, les règles découlent du tableau d'actions du chapitre 14.

| **Table** | **Lire** | **Créer** | **Modifier** | **Supprimer** |
|---|---|---|---|---|
| chapitres | L'auteur : tout. Le relecteur : les chapitres en Relecture ou Publié | L'auteur | L'auteur | L'auteur |
| commentaires | L'auteur : tout. Le relecteur : ses propres commentaires | Toute personne qui peut lire le chapitre, en son propre nom | L'auteur du commentaire (texte) ; l'auteur du livre (marquer traité) | L'auteur du livre |
| roles_utilisateurs | Chacun : ses propres lignes. L'auteur : toutes | L'auteur | Personne | L'auteur |
| relectures_ia | L'auteur | L'auteur, en son nom (la fonction serveur agit pour lui) | Personne | L'auteur |

Traduites en SQL, les règles de chapitres donnent ceci :

```text
-- EXEMPLE À ADAPTER : règles d'accès de la table chapitres
alter table public.chapitres enable row level security;
 
create policy "auteur lit tout" on public.chapitres
  for select to authenticated
  using ((select public.a_le_role('auteur')));
 
create policy "relecteur lit les chapitres soumis" on public.chapitres
  for select to authenticated
  using (statut in ('relecture', 'publie')
         and (select public.a_le_role('relecteur')));
 
create policy "auteur modifie" on public.chapitres
  for update to authenticated
  using ((select public.a_le_role('auteur')))
  with check ((select public.a_le_role('auteur')));
```

Et celles de commentaires, où apparaît la règle la plus fine :

```text
-- EXEMPLE À ADAPTER : règles d'accès de la table commentaires
alter table public.commentaires enable row level security;
 
create policy "lire ses commentaires, ou tout pour l'auteur"
  on public.commentaires for select to authenticated
  using (redige_par = (select auth.uid())
         or (select public.a_le_role('auteur')));
 
create policy "commenter un chapitre qu'on peut lire"
  on public.commentaires for insert to authenticated
  with check (
    redige_par = (select auth.uid())
    and exists (select 1 from public.chapitres c where c.id = chapitre_id)
  );
```

Trois détails de lecture. Plusieurs règles sur la même opération s'additionnent : l'auteur lit tout par la première, le relecteur les chapitres soumis par la seconde. La clause using filtre les lignes existantes, with check contrôle celles qu'on écrit. Et la condition exists (...) de la dernière règle s'exécute elle-même sous les règles de chapitres : un relecteur ne commente que ce qu'il peut lire, sans qu'on répète la liste des statuts.

L'écriture (select auth.uid()) fait calculer l'identifiant une fois par requête au lieu d'une fois par ligne, écart qui compte sur de grosses tables (chapitre 25).

:::attention La table verrouillée qui paraît vide
Activer la RLS sans écrire aucune règle bloque tout : les listes s'affichent vides, et l'on croit ses données disparues. La tentation est alors d'écrire une règle using (true), qui laisse tout passer. Si L'Atelier affiche soudain une liste vide après un changement, demandez en mode Chat quelles règles existent sur la table, avant toute correction.
:::

:::prompt Faire relire les règles d'accès
En mode Chat, sans rien modifier : pour chaque table de ce projet, dis-moi si la RLS est activée et traduis chaque règle en une phrase de français simple (« un relecteur peut lire... »). Compare ensuite avec les règles attendues que je te colle ci-dessous, et signale tout écart, toute opération sans règle, toute règle qui laisse tout passer et toute fonction security definer.

:::

### Le test des trois comptes

Les règles se vérifient à l'usage, pas à la lecture, avec trois comptes : un auteur, deux relecteurs. Le chapitre 18 en fait une recette complète ; dès maintenant, trois gestes suffisent.

:::notice Vérifier les droits de L'Atelier
1. Comme auteur, créez quatre chapitres, un par statut de Idée à Relecture.
2. Comme relecteur A, dans une fenêtre privée, vérifiez que seul le chapitre en Relecture apparaît.
3. Collez dans cette session l'adresse d'un chapitre en Brouillon copiée chez l'auteur : la page doit être vide ou refusée.
:::

L'étape 3 est celle qu'on saute, et la plus importante : si le relecteur voit le brouillon en tapant son adresse, la règle manque dans la base, quel que soit ce qu'affiche l'interface.

L'aperçu et l'application publiée partagent en général les mêmes données (chapitre 24) : nommez vos comptes de test « TEST relecteur A » et supprimez-les avant d'inviter les vrais relecteurs.

### Les captures d'écran : un garde-meuble privé

Les fichiers ne vont pas dans les tables. Ils vont dans le stockage de Cloud, organisé en *buckets*, et la table captures ne garde que le chemin de chaque fichier et sa légende.

:::fiche BUCKET · BRIQUE
**Définition.** Un espace de stockage de fichiers, dans le backend d'une application, doté de ses propres règles d'accès (le mot anglais veut dire « seau »).

**Analogie.** Un box de garde-meuble loué pour un usage précis, dont le gardien ne donne la clé qu'aux personnes inscrites sur sa liste.

**À ne pas confondre avec.** Un dossier sur votre ordinateur, ou un Drive partagé : un bucket n'a pas d'interface pour ses utilisateurs, seule l'application y accède.
:::

Sur Cloud, en septembre 2026, les buckets sont privés par défaut et leur accès se règle par RLS comme pour les tables. C'est le bon réglage : une capture d'écran peut montrer une adresse e-mail, parfois un morceau de clé.

Une convention simple suffit : chaque fichier est rangé dans un dossier qui porte l'identifiant de la personne qui l'a déposé, et les règles raisonnent sur ce chemin.

```text
-- EXEMPLE À ADAPTER : règles du bucket privé « captures »
create policy "déposer dans son dossier" on storage.objects
  for insert to authenticated
  with check (bucket_id = 'captures'
              and (storage.foldername(name))[1] = (select auth.uid())::text);
 
create policy "lire ses fichiers, ou tout pour l'auteur" on storage.objects
  for select to authenticated
  using (bucket_id = 'captures'
         and ((storage.foldername(name))[1] = (select auth.uid())::text
              or (select public.a_le_role('auteur'))));
```

Pour afficher une capture, l'application ne donne jamais l'adresse permanente du fichier. Elle génère une URL signée, qui expire au bout d'une heure sur Cloud.

:::fiche URL SIGNÉE · SÉCURITÉ
**Définition.** Une adresse web temporaire vers un fichier privé, accompagnée d'une signature qui prouve qu'elle a été délivrée par l'application, et qui cesse de fonctionner après un délai.

**Analogie.** Le ticket de vestiaire daté : il permet de récupérer le manteau ce soir, pas la semaine prochaine, et ne vaut que pour ce manteau.

**À ne pas confondre avec.** Une adresse publique, qui fonctionne pour tout le monde et pour toujours.
:::

L'export de la base ne comprend pas les fichiers du stockage, qui se sauvegardent à part, et le stockage reste facturé même quand le backend est en pause.

### Les fonctions serveur

Deux actions de L'Atelier manipulent un secret et ne peuvent donc pas se faire dans le navigateur : prévenir les relecteurs par e-mail, et demander une relecture à Claude. Elles vivent dans des fonctions serveur. Sur Cloud, les Edge Functions en sont la forme historique, que Lovable écrit et déploie lui-même ; depuis le 13 mai 2026, les nouveaux projets reposent sur TanStack Start, où la logique serveur peut aussi s'écrire en fonctions createServerFn. Dans les deux cas, un secret lu par le code ne voyage jamais jusqu'au navigateur.

Leurs limites sont modestes (chez Supabase, dont Cloud dérive, 256 Mo de mémoire et 2 secondes de calcul en septembre 2026, sans garantie pour Cloud) : attendre la réponse de Claude n'y pose aucun problème, fabriquer le PDF du livre en poserait.

Cloud envoie déjà les e-mails d'authentification ; pour l'e-mail métier aux relecteurs, la méthode Resend du chapitre 13 vaut ici, avec une clé propre à L'Atelier.

:::prompt Prévenir les relecteurs
Quand l'auteur passe un chapitre au statut Relecture, envoie un e-mail à chaque relecteur actif : « Le chapitre [numéro] ([titre]) attend votre relecture », avec un lien vers la fiche du chapitre. Utilise une fonction serveur et Resend ; la clé est dans les Secrets sous le nom RESEND_API_KEY. N'envoie rien si le chapitre était déjà en Relecture. Vérifie côté serveur que la personne qui déclenche l'envoi a le rôle auteur. Avant d'écrire le code, dis-moi ce que tu vas créer.
:::

Cloud propose aussi des tâches planifiées (*Jobs*), créées par le chat, par exemple un récapitulatif hebdomadaire pour l'auteur (« deux chapitres sans commentaire depuis sept jours »). Chaque exécution consomme de l'usage Cloud : une par semaine ne coûte presque rien, une par minute est une fuite discrète.

### Les secrets

Un secret est une valeur que le code serveur doit connaître et que personne d'autre ne doit voir : la clé Resend, bientôt la clé Anthropic. L'onglet Secrets est l'outil du réflexe du chapitre 7 (jamais de secret dans le chat ni dans le code).

Les secrets sont en écriture seule : la valeur ne peut plus être relue dans Lovable, gardez l'original dans un gestionnaire de mots de passe. Les préfixes SUPABASE_ et LOVABLE_ sont réservés. Et un remix ne copie pas les secrets : une variante de L'Atelier n'enverra rien tant que vous n'aurez pas recréé ses clés. Une clé collée par erreur dans le chat est une clé publiée : révoquez-la (chapitre 20).

### Les journaux et les sauvegardes

L'onglet Logs rassemble huit types de journaux, conservés environ cinq jours, qu'il faut rafraîchir à la main (*Refresh*). La méthode conseillée par Lovable est de coller une ligne d'erreur exacte dans le chat, en mode Chat ; le chapitre 18 en fait une méthode complète.

Côté données, Cloud prend un instantané de la base par jour et le conserve environ quatorze jours. On restaure un instantané, pas un moment quelconque, et tout ce qui a suivi est perdu : les commentaires de la journée disparaîtraient. Et revenir à une ancienne version dans l'historique de Lovable restaure le code, jamais les données.

:::astuce Le manuscrit ne vit pas dans L'Atelier
Ne faites pas de L'Atelier le seul endroit où existe le texte d'un chapitre. Le manuscrit a son lieu de travail, versionné (un dépôt GitHub, présenté au chapitre 6, peut l'accueillir) ; L'Atelier en reçoit une copie à relire. Exportez aussi chaque semaine les tables commentaires et relectures_ia en CSV, et rangez ces fichiers hors de Lovable. C'est rustique et gratuit.
:::

### Ce que coûte Cloud

Cloud est facturé à l'usage, en crédits de fonctionnement prélevés sur le même solde que les crédits de construction. En septembre 2026, chaque espace de travail Free, Pro ou Business reçoit chaque mois 20 crédits Cloud et 4 crédits IA, qui ne se reportent pas d'un mois sur l'autre. Au-delà, la consommation est prise sur les crédits généraux.

La vue Usage détaille les trente derniers jours par poste : base (taille de la machine multipliée par sa durée d'allumage), exécution de code, données transférées, stockage, temps réel, IA. Parmi les six tailles de machine, de Tiny à X-Large, la plus petite suffit pour commencer ; les métriques d'Advanced settings diront s'il faut monter.

:::cout Lovable Cloud pour L'Atelier, septembre 2026
Allocation mensuelle incluse (Free, Pro, Business) : 20 crédits Cloud et 4 crédits IA, sans report.

Valeur estimée d'un crédit : environ 0,25 $ sur Pro (calcul publié par un site tiers), soit de l'ordre de 5 $ pour l'allocation Cloud.

Recharge : 0,30 $ le crédit sur Pro, 0,60 $ sur Business, valable 12 mois.

Crédits par heure selon la taille de la machine : non publiés dans la documentation lue, à lire dans Advanced settings.

Pour un outil interne de quelques utilisateurs, je ne peux pas vous promettre que l'allocation suffira : relevez la vue Usage chaque semaine pendant le premier mois, c'est votre seule mesure fiable.
:::

Un dernier mécanisme doit être connu avant d'inviter qui que ce soit. Quand le solde de crédits tombe à zéro, selon la documentation, le site publié reste en ligne, mais les applications qui reposent sur Cloud peuvent être mises en pause jusqu'au rechargement, et un backend en pause se relance à la main. Pour L'Atelier, cela voudrait dire des relecteurs devant une liste vide un dimanche soir.

:::attention Solde à zéro, relecteurs à la porte
Activez les recharges automatiques dès que de vrais relecteurs utilisent L'Atelier, et désactivez la pause automatique pour inactivité, qui convient aux prototypes abandonnés mais pas à un outil en service. Les plafonds par membre réglables dans Settings ne concernent que les crédits de construction : ils ne protègent pas l'application.
:::

Le budget, réflexe du chapitre 7, prend ici sa forme concrète : une ligne dans votre carnet de bord, chaque lundi, avec la consommation de la semaine et le poste le plus lourd.

:::bref Lovable Cloud donne à L'Atelier une base PostgreSQL, des comptes, un stockage et des fonctions serveur ; la région (Europe) se choisit une fois pour toutes.
Les tables naissent par des migrations relues ; l'éditeur SQL sert à lire, pas à écrire.

Les rôles vivent dans une table à part, interrogée par une petite fonction ; les règles RLS s'écrivent d'abord en français, puis en SQL, puis se vérifient avec trois comptes.

Les captures dorment dans un bucket privé, montrées par des URL signées d'une heure ; les secrets sont en écriture seule et absents des remix.

Sauvegardes de quatorze jours sans les fichiers, crédits de fonctionnement à surveiller, recharges automatiques en service.
:::
