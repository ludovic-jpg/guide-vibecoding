Le mot « application » vient du latin *applicare*, « appliquer, mettre contre, attacher à ». Une application est un programme que l'on applique à une tâche précise : prendre des rendez-vous, suivre des chapitres, encaisser un abonnement. Le mot dit l'usage. Il ne dit rien de ce qu'il y a derrière.

Or, derrière le moindre bouton « S'inscrire », plusieurs pièces jouent des rôles très différents. Quand quelque chose casse, ou quand quelqu'un lit des données qu'il ne devrait pas voir, il faut savoir dans quelle pièce chercher, et le dire à l'IA. Un prompt qui dit « le calcul se fait côté serveur » obtient un tout autre résultat qu'un prompt qui dit « fais le calcul ».

Pour distinguer ces pièces, je vous propose une maison. Elle a ses défauts (je les dirai à la fin), mais un mérite rare : chacun de nous sait déjà qu'une cuisine n'est pas un salon, et qu'on ne donne pas à un invité la clé de la chaufferie.

### La façade et les pièces de réception : le front

Le *frontend*, qu'on abrège en « front », est la partie visible de l'application, celle qui s'affiche dans votre navigateur ou sur votre téléphone : les pages, les boutons, les formulaires, les menus. Dans la maison, c'est la façade, l'entrée et le salon, les pièces où l'on reçoit.

Trois langages le composent : le HTML pour la structure (un titre, un formulaire), le CSS pour l'apparence (couleurs, disposition), le JavaScript pour le comportement (le menu qui se déplie, le champ qui rougit quand l'adresse est mal saisie).

Pour le site vitrine du Guide, le front sera presque tout.

:::fiche FRONTEND · BRIQUE
**Définition.** La partie visible de l'application, qui s'affiche et s'exécute dans le navigateur ou le téléphone du visiteur.

**Analogie.** La façade et les pièces où l'on reçoit.

**À ne pas confondre avec.** Le backend, qui tourne sur un serveur et que le visiteur ne voit jamais.
:::

### La cuisine et la chaufferie : le back

Le *backend*, ou « back », est la partie invisible. Il tourne sur un serveur, un ordinateur distant. Il applique les règles, fait les calculs, parle à la base de données et aux services extérieurs. Dans la maison, ce sont la cuisine, la chaufferie, le tableau électrique : personne ne les visite, tout en dépend.

Pour l'inscription à la lettre du site, le front affiche le champ et le bouton ; le back vérifie que l'adresse n'est pas déjà inscrite, l'enregistre et fait expédier la confirmation. Si cette logique vivait dans le navigateur, un visiteur curieux pourrait la contourner : ce qui s'exécute chez lui, il peut le lire et le modifier.

Retenez la règle, parce qu'elle reviendra souvent : ce qui doit rester vrai quoi que fasse le visiteur (un prix, un droit d'accès, une limite) doit être appliqué là où le visiteur n'entre pas.

### Le cellier et ses registres : la base de données

La base de données est l'endroit où l'application range durablement ce qu'elle doit retenir : les abonnés, les chapitres, les commentaires, les clients. Elle s'organise en tables, un peu comme les onglets d'un classeur. Chaque table est faite de lignes (un abonné) et de colonnes (son adresse, sa date d'inscription). Dans la maison, c'est le cellier bien rangé, avec un registre sur chaque étagère.

Pour L'Atelier, on devine déjà quelques tables : les chapitres (statuts Idée, Brouillon, Rédaction, Relecture, Publié), les relecteurs, les commentaires. Le chapitre 14 les dessinera.

Lovable s'appuie pour cela sur Lovable Cloud, lancé le 29 septembre 2025, qui fournit une base de données PostgreSQL, la gestion des comptes, un espace de stockage de fichiers et du code côté serveur, sans compte séparé à créer. En coulisses, Lovable Cloud repose sur Supabase, que nous retrouverons au chapitre 15 et, si vous choisissez un jour de reprendre la main, au chapitre 19.

### La réserve : le stockage de fichiers

Les objets volumineux (images, PDF, vidéos) vont dans un espace de stockage de fichiers, et la base ne garde que leur adresse, comme le registre du cellier indique « carton n° 12, au fond à gauche ». L'Atelier y rangera ses captures d'écran. Et la réserve pose la même question que le reste de la maison : qui a le droit d'y entrer ?

### Le guichet : l'API

Une application vit rarement seule. Pour encaisser un paiement, elle s'adresse à Stripe. Pour envoyer un e-mail, à Resend. Pour faire relire un chapitre, à Claude. Chaque fois, elle passe par une API, un guichet normalisé par lequel deux logiciels échangent des demandes et des réponses selon des formes convenues.

:::mot Ce qui se tient entre deux faces
API signifie *Application Programming Interface*, interface de programmation d'application. Le mot qui compte est le dernier. « Interface » assemble le latin *inter*, « entre », et *facies*, « la face » : ce qui se tient entre deux faces, la surface où deux mondes se touchent sans se mélanger.

Au guichet de la poste, vous ne voyez pas le centre de tri, et le guichetier ne voit pas votre salon. L'échange a lieu quand même, parce que chacun respecte les formes : le bon formulaire, le bon timbre, la bonne case.

L'analogie s'arrête sur un point qui a son importance. Au guichet, on peut expliquer, négocier, se reprendre ; le guichetier devine ce que vous vouliez dire. Une API ne devine rien. Une virgule de travers, un champ mal nommé, et le guichet répond par un refus sec, sous forme d'un code d'erreur. Quand quelque chose échoue, transmettez donc à l'IA le message d'erreur exact.
:::

Un guichet exige presque toujours une pièce d'identité : la clé d'API, mot de passe technique qui dit au service « c'est bien moi, et c'est moi qui paie ». Elle ne doit jamais se trouver dans le front ; selon la documentation de Lovable, un secret placé dans le code du navigateur doit être considéré comme compromis. Les clés se rangent dans la rubrique des secrets et ne servent que depuis le back. C'est l'un des réflexes du chapitre 7, et le chapitre 16 l'appliquera à la clé Anthropic de L'Atelier.

:::fiche API · BRIQUE
**Définition.** Interface par laquelle un logiciel adresse des demandes à un autre et reçoit des réponses, selon des formes strictement définies.

**Analogie.** Le guichet de la poste : on ne voit pas l'arrière-boutique, on respecte les formulaires.

**À ne pas confondre avec.** La clé d'API, qui est la pièce d'identité présentée au guichet, et qui doit rester secrète.
:::

### La serrure et le badge : authentification et autorisation

Deux mots se ressemblent, et leur confusion est à l'origine de bien des incidents du vibe coding.

L'authentification vérifie qui vous êtes. C'est la serrure de la porte d'entrée : mot de passe, lien magique reçu par e-mail, connexion avec un compte Google. L'autorisation vérifie ce que vous avez le droit de faire une fois entré. C'est le badge, qui ouvre certaines portes intérieures et pas d'autres.

Dans L'Atelier, l'authentification garantit que la personne connectée est bien l'une des relectrices invitées. L'autorisation garantit qu'elle voit les chapitres au statut Relecture ou Publié, qu'elle peut y laisser des commentaires, mais qu'elle ne peut ni changer le statut d'un chapitre ni lire les notes de l'auteur. Dans le SaaS d'audit, l'enjeu grandit encore : chaque client ne doit voir que ses propres rapports, jamais ceux d'un concurrent qui utilise le même service.

:::fiche AUTORISATION · SÉCURITÉ
**Définition.** Ensemble des règles qui fixent ce qu'une personne connectée a le droit de voir et de faire dans l'application.

**Analogie.** Le badge qui ouvre certaines portes intérieures et pas d'autres.

**À ne pas confondre avec.** L'authentification, qui vérifie seulement l'identité, comme la serrure de la porte d'entrée.
:::

:::attention Une application qui marche peut être grande ouverte
Des applications vibecodées dont tout fonctionnait à l'écran ont exposé leurs données faute de règles d'accès : porte d'entrée verrouillée, pièces intérieures grandes ouvertes (récits au chapitre 20). Tester que « ça marche » ne dit rien de qui peut lire vos données : testez avec deux comptes différents, comme au chapitre 15.
:::

### Le terrain et l'adresse : hébergement et domaine

Une application doit tourner en permanence sur des serveurs qui répondent aux visiteurs : c'est l'hébergement, le terrain de la maison. Avec Lovable, le terrain est fourni : quand vous cliquez sur Publish, l'application est mise en ligne sur l'infrastructure de la plateforme.

Le nom de domaine, par exemple guide-vibecoding.fr (nom d'exemple), est l'adresse lisible de la maison. Le déploiement est l'action de publier une nouvelle version. Le chapitre 12 détaille l'achat du domaine et son branchement.

### Le kit de construction : le framework

Un framework est une boîte à outils structurée qui impose une manière d'organiser le code et évite de tout réinventer. Pensez à une maison en kit : l'emplacement des murs porteurs, le passage des gaines et la numérotation des pièces sont déjà prévus.

Les outils de vibe coding s'appuient sur des kits très répandus : React, créé par Meta, construit les interfaces à partir de composants réutilisables ; TypeScript ajoute à JavaScript des « types » qui détectent des erreurs avant l'exécution ; Tailwind CSS habille les éléments de petites classes toutes prêtes. Depuis le 13 mai 2026, les nouveaux projets Lovable reposent sur TanStack Start, toujours en React et TypeScript, avec un rendu qui peut se faire côté serveur : le visiteur, et le moteur de recherche avec lui, reçoit une page complète plutôt qu'une page vide que le navigateur remplit ensuite.

Ces kits abondent dans le code public : les IA les connaissent très bien, et un développeur reprendra votre code sans dépaysement.

### Les archives du chantier : le dépôt

Le dépôt (*repository*, ou « repo ») est le dossier du projet placé sous gestion de versions, le plus souvent sur GitHub. Chaque modification y laisse une trace datée et décrite ; on peut revenir en arrière, comparer deux états, essayer une variante sans toucher à l'original.

C'est le carnet de chantier de votre maison, avec une photo de chaque étape. Le jour où l'IA cassera quelque chose, et ce jour viendra, c'est lui qui vous permettra de retrouver la dernière version qui fonctionnait. C'est aussi lui qui rend votre code lisible par d'autres outils que Lovable, y compris Claude, comme nous le verrons au chapitre 6. Des enregistrements fréquents et bien nommés font partie des réflexes du chapitre 7.

### Trois maisons pour un même livre

Nos trois axes n'ont pas besoin des mêmes pièces : nous les ajouterons une à une.

| **Pièce** | **Site vitrine (partie 3)** | **L'Atelier (partie 4)** | **SaaS d'audit (partie 5)** |
|---|---|---|---|
| Front | Presque tout le projet | Tableau de bord des chapitres | Questionnaire, espace client, rapports |
| Back | Inscriptions, envoi d'e-mails | Règles de statut, appels à Claude | Préparation des audits, abonnements |
| Base de données | Abonnés à la lettre | Chapitres, relecteurs, commentaires | Clients, projets audités, rapports |
| Stockage de fichiers | Couverture, extraits | Captures d'écran | Rapports téléchargeables |
| API extérieures | Resend, Stripe | Claude, Resend | Claude, Stripe, Resend |
| Authentification | Aucune pour les visiteurs | Comptes auteur et relecteurs | Comptes clients |
| Autorisation | Minime | Rôles et droits par chapitre | Isolation stricte entre clients |
| Secrets | Clés Stripe et Resend | Clé Anthropic | Toutes les clés, plus la facturation |

De gauche à droite, la maison grandit, et avec elle la part de ce qui ne se voit pas. Le site vitrine est presque tout en façade ; le SaaS est un immeuble où chaque locataire doit avoir sa clé, et seulement la sienne. D'où l'ordre du livre : on apprend à poser une serrure avant de gérer un trousseau.

:::prompt Faire l'inventaire des pièces d'un projet
Voici la description de l'application que je veux construire : [décrivez-la en cinq à dix lignes].

En utilisant l'analogie de la maison, dresse l'inventaire des pièces dont elle aura besoin : front, back, base de données (quelles tables ?), stockage de fichiers, API extérieures, authentification, autorisation (qui voit quoi ?), secrets.

Pour chaque pièce, dis en une phrase pourquoi elle est nécessaire, ou pourquoi elle ne l'est pas. Signale les points où une erreur exposerait des données personnelles.

Ne propose pas encore de code ni d'outil : je veux seulement comprendre la structure.
:::

Faites cet exercice pour le site vitrine du Guide dès maintenant, et collez la réponse dans votre carnet de bord. Vous la relirez au chapitre 10, en rédigeant le cahier des charges du site.

### Où l'analogie s'arrête

Une maison, une fois construite, change peu. Une application vit : ses briques reçoivent des mises à jour de sécurité, les services auxquels elle se branche modifient leurs guichets, les données s'accumulent et doivent être sauvegardées.

Dans une maison, la cloison entre la cuisine et le salon se voit. Dans une application, rien à l'écran ne dit ce qui s'exécute dans le navigateur et ce qui s'exécute sur le serveur : demandez-le explicitement (« où ce calcul s'exécute-t-il ? », « cette clé est-elle visible dans le navigateur ? »).

Enfin, l'architecte, le maçon et le plombier d'une maison sont des personnes distinctes, qui se contredisent parfois. Dans le vibe coding, une seule IA tient tous les rôles, et elle ne signale pas qu'elle a posé la chaufferie dans le salon. Le maître d'ouvrage, celui qui réceptionne le chantier, c'est vous.

:::bref Le front est la façade visible ; le back est la cuisine invisible, où s'appliquent les règles qui doivent rester vraies quoi que fasse le visiteur.
La base de données range les informations en tables, le stockage garde les fichiers, l'API est le guichet entre logiciels.

L'authentification dit qui vous êtes, l'autorisation ce que vous pouvez voir ; les confondre ouvre des failles que l'écran ne montre pas.

Les secrets se rangent dans un coffre côté serveur ; le dépôt GitHub est le carnet de chantier qui permet de revenir en arrière.

Le site vitrine, L'Atelier et le SaaS demandent de plus en plus de pièces invisibles, ce qui explique l'ordre du livre ; et contrairement à une maison, une application vit et s'entretient.
:::
