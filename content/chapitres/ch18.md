Le mot anglais *bug* désigne un insecte. Les ingénieurs l'employaient bien avant l'informatique pour nommer le petit défaut caché qui fait dérailler une machine. L'image rappelle que l'insecte ne se montre pas là où il niche, mais là où il fait des dégâts : le commentaire qui « disparaît » dans L'Atelier se cache probablement loin de l'écran qui l'affiche, dans une règle d'accès, une fonction serveur, un champ mal nommé.

Déboguer, c'est remonter de la trace au nid. Lire le code n'y est pas indispensable : il faut une méthode, savoir quoi montrer à Claude ou à Lovable, et savoir s'arrêter quand on tourne en rond. L'autre moitié du travail évite d'avoir à déboguer : tester et recetter avant que les relecteurs ne s'en chargent.

:::mot Tester, ou le pot de l'orfèvre
« Test » est un mot que le français a prêté à l'anglais avant de le reprendre. En ancien français, le *test* (du latin *testum*, vase de terre) désignait le petit pot où l'on éprouvait les métaux précieux : on y chauffait l'or pour séparer le pur de l'alliage. Tester, c'était soumettre une matière à une épreuve dont on connaissait d'avance le résultat attendu.

Tout est déjà là. Un test est une épreuve préparée, pas une promenade pour « voir si ça marche » : on sait ce que l'or pur doit donner, et l'on regarde si le métal le donne. Sans résultat attendu écrit d'avance, on ne teste rien, on constate, et l'on finit par trouver normal ce que l'application fait, simplement parce qu'elle le fait.
:::

### Décrire avant de réparer

Un bon signalement de bug a trois parties : ce que j'ai fait, ce que j'attendais, ce qui s'est passé. « Les commentaires ne marchent pas » tient du soupir. « Connecté comme relecteur, j'ai commenté le chapitre 9, j'attendais de voir mon commentaire, la liste est restée vide après rechargement » est un signalement.

Ajoutez le message d'erreur exact. Dans Lovable, l'agent lit lui-même la console et les échanges réseau de l'aperçu. Pour le côté serveur, les journaux de *Cloud*, puis *Logs*, présentés au chapitre 15, donnent la ligne à coller dans le chat : copiez le texte plutôt qu'une capture, et jamais une clé secrète.

:::astuce Un gabarit de signalement pour les relecteurs
Mettez les trois questions (« Qu'avez-vous fait ? Qu'attendiez-vous ? Que s'est-il passé ? ») dans le formulaire de contact de L'Atelier, avec un champ pour une capture. Vous recevrez des signalements prêts à coller dans Lovable plutôt que des « ça bugue ».
:::

:::prompt Chercher la cause avant la correction
Voici un bug dans L'Atelier. Ce que j'ai fait : [action]. Ce que j'attendais : [attente]. Ce qui s'est passé : [résultat]. Message d'erreur exact : [collez-le].

Avant de corriger quoi que ce soit, explique-moi en français simple la cause profonde, montre-moi le code ou la règle concernés et propose une correction. N'applique rien tant que je n'ai pas validé.
:::

Ce conseil vient de la documentation de Lovable, et il vaut pour Claude Code. Une IA à qui l'on dit « corrige » bouche volontiers le trou visible, par exemple en empêchant une valeur vide de faire planter la page, sans se demander pourquoi la valeur était vide. Le mode Plan (chapitre 6) est l'endroit naturel de cette enquête : il inspecte fichiers, base et journaux sans rien modifier.

### La règle des deux échecs

Lovable propose un bouton *Try to fix*, gratuit dix fois par 24 heures, et conseille de ne pas s'en servir plus d'une ou deux fois de suite. La règle vaut pour tous les outils : après deux échecs sur le même problème, on change de geste.

Le motif est connu : on corrige, l'IA casse autre chose, on corrige encore, et chaque tour consomme des crédits, même ceux qu'on annule ensuite. Voici les gestes, rangés par symptôme.

| **Ce que vous voyez** | **Cause probable** | **Le geste** |
|---|---|---|
| L'IA annonce « corrigé », rien ne change | Elle devine sans voir l'erreur | Faites ajouter des traces dans la console, reproduisez le bug, donnez-lui ce qui s'affiche |
| Une fonction qui marchait a disparu | Elle a réécrit tout un fichier pour une retouche | Revenez à la version précédente, redemandez avec « ne modifie que [tel élément] » |
| Elle oublie des consignes données plus tôt | La conversation déborde de sa fenêtre de contexte | Nouvelle conversation avec un résumé de passation ; dans Claude Code, /compact ou /clear |
| Chaque correction crée deux bugs | Demande trop grosse ou zone fragile | Retour à la dernière version saine, puis une petite demande par message |
| Elle se contredit d'un message à l'autre | Elle ignore la cause et tente au hasard | Mode Plan dans Lovable ou dans Claude Code : elle enquête sans rien modifier |
| Rien de tout cela ne marche | L'outil est à court d'idées | Second avis dans une conversation Claude neuve, puis un humain |

Le retour en arrière paraît un renoncement ; on n'y perd que la mauvaise piste. Dans Lovable, *Revert and resend* sur l'ancien message reformule la demande à partir de l'état qui marchait ; il restaure le code, jamais les données. Le second avis, lui, vaut par son ignorance : une conversation neuve, dans le projet Claude « Guide, Atelier », sans l'historique enlisé, voit souvent ce que la première ne voyait plus. Demandez-lui une explication, pas une correction. Pour changer de conversation sans tout perdre, le résumé de passation du chapitre 2 sert tel quel, en y ajoutant le message d'erreur exact et ce qui a déjà été essayé.

Appelez un humain quand le problème touche aux paiements, aux données personnelles ou aux droits d'accès, ou quand vous ne savez plus dans quel état est le projet : une heure de développeur coûte moins qu'une semaine de crédits en boucle (chapitre 29).

### Les bugs typiques de L'Atelier

Une application comme L'Atelier produit toujours à peu près les mêmes insectes. Les voici, avec leur nid le plus fréquent.

Le relecteur ne voit rien. Il est connecté, le chapitre existe, la liste des commentaires est vide. Le plus souvent, la table est sous RLS (chapitre 15) sans règle de lecture : elle paraît vide, sans message d'erreur. Le correctif consiste à écrire la règle qui manque, par exemple « un relecteur lit ses propres commentaires ».

Le relecteur voit trop. Il aperçoit les commentaires d'un autre relecteur, ou peut passer un chapitre de « Relecture » à « Publié ». Soit une règle laisse tout passer, soit le contrôle du rôle n'existe que dans l'interface : on a caché le bouton, on n'a pas fermé la porte. C'est le bug le plus grave, parce que rien ne le signale ; seule la recette, plus bas, le révèle.

La capture d'écran refuse de partir, ou s'affiche pour l'auteur et pas pour le relecteur. Le stockage a ses propres règles d'accès, distinctes de celles des tables, et on oublie souvent de les écrire.

La relecture par Claude renvoie une erreur 401 ou 500. Le secret de la clé Anthropic manque ou porte un autre nom que celui lu par le code, la fonction ne transmet pas l'identité de l'utilisateur, ou le plafond de dépense de la Console est atteint : les journaux de la fonction disent lequel.

Le commentaire apparaît deux fois, après un double clic sur « Envoyer ». On désactive le bouton pendant l'envoi et, pour les opérations qui comptent, on empêche le doublon côté base.

L'e-mail n'arrive pas. Domaine d'envoi mal vérifié chez Resend (chapitre 13), rebond ou indésirables : sans tableau de bord d'envoi, impossible de trancher, et c'est l'argument principal pour passer par Resend.

:::fiche TRACE · MÉTHODE
**Définition.** Une ligne que le programme écrit volontairement dans la console ou les journaux à un moment choisi (« commentaire reçu », « utilisateur : relecteur », « réponse de la base : 0 ligne ») pour qu'on puisse suivre son chemin.

**Analogie.** Les cailloux blancs du Petit Poucet : on les sème à l'aller pour savoir, au retour, jusqu'où on est allé.

**À ne pas confondre avec.** Le message d'erreur, que le programme produit seul quand il échoue ; la trace, on la demande.
:::

### Le décodeur des erreurs fréquentes

| **Message ou symptôme** | **Ce que ça veut dire** | **Quoi faire** |
|---|---|---|
| Page blanche, sans message | Une erreur a bloqué l'affichage ; elle est écrite dans la console | Donnez la première ligne rouge à l'IA |
| 401 Unauthorized | L'application ne sait pas qui vous êtes : pas connecté, session expirée ou clé absente | Reconnectez-vous ; sinon, faites vérifier l'identification |
| 403 Forbidden | Elle sait qui vous êtes et vous refuse l'action | Vérifiez avec quel compte vous testez ; demandez quelle règle bloque |
| permission denied ou violates row-level security policy | La RLS refuse l'opération | Demandez une règle précise, jamais la suppression de la RLS |
| Build failed | Le code ne peut pas être assemblé | Les premières lignes désignent le fichier fautif |
| Module not found | Une bibliothèque manque, ou un fichier est appelé à la mauvaise adresse | Le message tel quel à l'IA ; en local, installez les dépendances |
| window is not defined | Sur un projet TanStack Start, du code prévu pour le navigateur s'exécute sur le serveur | Signalez-le tel quel, en précisant la page concernée |

:::attention Ne jamais « réparer » la sécurité en l'enlevant
Face à une erreur de permission, une IA pressée propose parfois de désactiver la RLS, d'écrire une règle qui laisse tout passer, ou d'utiliser une clé qui contourne toutes les règles. L'erreur disparaît, la protection aussi. Refusez : le bon correctif ajoute une règle (chapitre 20).
:::

### Recetter L'Atelier avec deux comptes

Le meilleur bug est celui qu'on trouve avant les relecteurs, par une vérification dont le nom vient du bâtiment.

:::fiche RECETTE · MÉTHODE
**Définition.** La série de vérifications faites sur une application avant de l'accepter, en comparant pour chaque scénario le résultat attendu, écrit d'avance, au résultat obtenu.

**Analogie.** Le tour du chantier avec l'entrepreneur avant la remise des clés, liste de réserves à la main.

**À ne pas confondre avec.** Un test automatisé, que la machine rejoue seule ; la recette est faite par un humain qui joue l'utilisateur.
:::

Pour L'Atelier, il faut trois comptes (auteur, relecteur A, relecteur B) et deux navigateurs, ou une fenêtre privée, pour rester connecté à deux à la fois.

| **Scénario** | **Compte** | **Saisie** | **Résultat attendu** | **Obtenu** | **OK ?** |
|---|---|---|---|---|---|
| Ouvrir un chapitre en relecture | Relecteur A | Chapitre 9 | Le texte s'affiche, le bouton Commenter aussi |  |  |
| Commenter | Relecteur A | « Paragraphe 3 obscur » | Le commentaire apparaît, signé A |  |  |
| Voir le commentaire d'un autre | Relecteur B | Chapitre 9 | Invisible (règle du chapitre 14) |  |  |
| Modifier le commentaire d'un autre | Relecteur B | Tentative sur celui de A | Refus clair |  |  |
| Changer un statut | Relecteur A | Relecture vers Publié | Refus : réservé à l'auteur |  |  |
| Ouvrir un chapitre non partagé | Relecteur B | Chapitre 20, resté en Brouillon | Invisible, même par son adresse directe |  |  |
| Envoyer une capture | Relecteur A | Image de 2 Mo | Visible pour A et pour l'auteur |  |  |
| Lancer la relecture Claude | Auteur | Chapitre 9 | Un retour en moins d'une minute, coût enregistré dans relectures_ia |  |  |
| Lancer la relecture Claude | Relecteur A | Chapitre 9 | Refus 403 : réservé à l'auteur |  |  |
| Dépasser le quota | Auteur | 31e relecture du mois | Message « Quota mensuel atteint » (chapitre 16) |  |  |

Remplissez les quatre premières colonnes avant de tester. Chaque « non » devient un signalement de bug tout prêt. La ligne « même par son adresse directe » est celle que l'on oublie : un chapitre absent du menu n'est pas protégé pour autant.

Un vrai utilisateur, lui, ne suit pas le scénario. Ajoutez des saisies absurdes.

:::checklist Les saisies absurdes
☐  Chaque formulaire validé avec tous les champs vides

☐  Un commentaire de plusieurs milliers de caractères, avec apostrophes et guillemets (« L'Atelier d'Hélène »)

☐  Un fichier de 50 Mo, puis un fichier qui n'est pas une image renommé en .png

☐  Un double clic sur chaque bouton qui enregistre

☐  Une session laissée ouverte une nuit, puis une action le matin

☐  Le parcours du relecteur refait sur un téléphone
:::

### Faire tester par les machines

La recette humaine coûte une heure, donc on la refait rarement. Pour les parcours qui comptent, faites-la rejouer par une machine. Lovable propose des tests dans le navigateur : l'agent ouvre l'application, clique, remplit, et rapporte ce qu'il voit. Depuis le 8 septembre 2026, il sait se connecter pendant ces tests, ce qui permet de vérifier un parcours de relecteur ; selon la documentation, cette commodité est propre à Lovable Cloud. Lovable sait aussi écrire des tests automatisés de l'interface et des fonctions serveur.

:::prompt Faire jouer la recette à Lovable
Utilise les tests dans le navigateur (browser testing) pour vérifier ce parcours dans L'Atelier : connecte-toi avec le compte de test « relecteur A », ouvre le chapitre 9, ajoute un commentaire, recharge la page et vérifie qu'il est toujours là. Puis connecte-toi avec « relecteur B » et vérifie qu'il ne peut ni modifier ni supprimer ce commentaire. Rapporte chaque étape avec le résultat attendu et le résultat obtenu. Ne modifie pas le code.
:::

Côté Claude Code, la skill webapp-testing d'Anthropic apprend à Claude à tester une application web avec Playwright, une bibliothèque qui pilote un vrai navigateur. Et Simon Willison recommande, dans son guide de février 2026 sur l'ingénierie agentique, la méthode dite rouge puis vert : faire écrire d'abord un test qui échoue, puis le code qui le fait passer. Pour un bug de L'Atelier, cela donne une consigne simple : « écris d'abord un test qui reproduit le bug, montre-moi qu'il échoue, puis corrige ». Si le bug revient, le test le signale.

Limitez ces tests aux trois à cinq parcours dont dépend le projet : se connecter, commenter, changer un statut, lancer la relecture. Tester tout est un projet en soi.

:::astuce Un bug résolu est une leçon à ranger
Quand un bug vous a coûté plus d'une heure, demandez à l'agent de résumer en trois lignes la cause et la règle à retenir. La règle va dans la Knowledge du projet, la leçon dans votre carnet de bord (chapitre 5).
:::

:::bref Un bon signalement : action, attente, résultat, message d'erreur exact ; les journaux de Lovable Cloud se lisent dans Logs, environ cinq jours.
La cause profonde avant la correction ; après deux échecs, on change de geste : traces, retour arrière, passation, mode Plan, second avis, humain.

Les bugs de L'Atelier nichent surtout dans les règles d'accès : liste vide faute de règle, relecteur qui voit trop, stockage sans règle ; on ajoute des règles, on n'en retire jamais.

La recette se prépare par écrit et se joue avec au moins deux comptes de relecteurs, adresse directe comprise, puis avec des saisies absurdes.

Les parcours qui comptent se font rejouer par les machines : tests dans le navigateur de Lovable, Playwright avec Claude Code, test rouge puis vert.
:::
